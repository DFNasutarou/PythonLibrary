# スニペット作成方針

## 目的

AtCoder主催のプログラミングコンテスト対策として、頻出のアルゴリズム・データ構造・便利メソッドをVS Codeスニペット化し、コンテスト本番で素早く正確に呼び出せるようにする。

## 基本原則

- **速さ最優先**：コンテスト中に「思い出す→調べる→書く」の時間をゼロに近づける。書き方を覚えることではなく、`prefix`を打って展開するだけで動く状態にすることがゴール。
- **正しさ最優先**：展開したコードは検証（AtCoderの提出 or verify-library的なテスト）を通ったものだけを収録する。未検証のものは`description`に明記する。
- **読みやすさより実用性**：本番用コードなので、多少の圧縮（短い変数名・1行化）は許容する。ただし後述の最低限の可読性ルールは守る。

## ファイル構成

- カテゴリ別に`.vscode/NN-カテゴリ名.code-snippets`として分割する（例: `01-basic`, `02-data-structure`, `03-graph`...）。
- 番号はエクスプローラ上の並び順の制御のみが目的で、優先度や重要度を表さない。
- 使われなくなった・上位互換に統合されたスニペットは削除せず`09-archive.code-snippets`に退避する（過去の提出コードとの整合性や、稀に劣化再現が必要な場合のため）。
- 新規スニペットは`99-template.code-snippets`の`Sample`エントリをコピーして雛形として使う。

## prefix（呼び出しキー）の命名規則

- **短く、打ちやすく**：英語 or ローマ字で3〜10文字程度。シフトキーや記号を含めない。
- **衝突を避ける**：既存の`prefix`一覧（`grep '"prefix":' .vscode/*.code-snippets`で確認可能）と重複・前方一致し過ぎないようにする。前方一致しすぎると別候補が埋もれてIntelliSenseの選択コストが増える。
- **命名パターン**：
  - データ構造・アルゴリズム名はそのまま（例: `dijkstra`, `unionfind`→`union`, `segtree`→`seg`）。
  - 亜種・派生形は基本形に接尾辞を足す（例: `union` → `union_potential`, `union_persist`）。
  - 日本語ローマ字表記は英語表記が長すぎる/一般的でない場合のみ許容する（例: `nibutan`, `saiki`）が、可能なら英語を優先する。
- 1つの`prefix`は1つの用途に固定する。既存の挙動を壊す上書き変更をしない（別の`prefix`として追加する）。

## description（説明文）の記述規則

- 日本語で1行、以下を含める：
  1. 何をするものか（アルゴリズム名・データ構造名）
  2. 主要な機能・切り替えオプション（例: 最大/最小切替、0-indexed/1-indexedなど）
  3. 可能なら計算量（例: `O(N log N)`）
- 未検証のものは先頭に`[未検証]`を付ける。

## body（実装本体）の記述方針

- **標準ライブラリのみ**に依存する（AtCoderのPython/PyPy実行環境で追加インストールなしに動くこと）。CPython/PyPy3両方で動作することを基本とする。
- **インデントは半角スペース2つ**に統一する（既存スニペットと合わせ、提出コードの行数・文字数を抑える）。
- **使い方コメントを本体末尾に必ず複数行で添付**する。1行の要約ではなく、`# `を外すだけでそのまま動く実行例をブロックで書く。

  ```
  # usage
  # uni = Union(N)
  # uni.merge(x, y)
  ```

  呼び出し例は代表的なメソッド呼び出しの流れが一連の手順として分かるように、必要なら複数行に分けて書く。
- **挙動を切り替えられる引数**を用意し、コピペ後の書き換え箇所を減らす（例: `is_max`, `default`など）。
- **クラス化・関数化して名前空間を汚さない**。トップレベルに汎用的すぎる変数名（`i`, `n`, `x`等）をむき出しで定義しない。展開後に他のコードと変数名が衝突しないようにする。
- **クラスにする場合はクラス直下に説明コメントを添え、各メソッドが何をするかを一言ずつ書く**。実装を読まなくてもクラス定義部分だけ見れば使い方が分かる状態にする。
- **利用者が直接呼ばない内部専用メソッドにはメソッド名の先頭に`_`を付け、クラス直下の説明コメントには載せない**。説明コメントに書くのは公開メソッドのみとし、内部実装の情報で「使い方」を埋もれさせない。
- **内部状態が複雑なクラスには、現在のデータを分かりやすく`print`表示するデバッグ用メソッドを用意する**。小さい入力での動作確認が目的なので、理想的な計算量である必要はない（全件を愚直に舐めて表示するだけでよい）。

  ```python
  class Union:
    # Union-Find（素集合データ構造）
    #   find(x): xの属する集合の代表元を返す
    #   merge(x, y): xとyの集合を併合する
    #   same(x, y): xとyが同じ集合かを返す
    #   size(x): xの属する集合の要素数を返す
    #   debug(): 各集合の中身を print する（動作確認用、計算量は問わない）
    def __init__(self, n):
      ...
    def _find_root(self, x):
      # 内部専用（説明コメントには載せない）
      ...
    def debug(self):
      print({r: self._members(r) for r in self._roots()})
  ```
- **出典URLを必ず入れる**（AtCoder生成AI対策ルールで、事前公開した生成AI製コードの使用時に参照URLの添付が必要なため）。URLは`main`ブランチの該当ファイル（例: `https://github.com/DFNasutarou/PythonLibrary/blob/main/acpython/.vscode/03-graph.code-snippets`）とする。
  - クラスがある場合：トップレベルの全クラスのクラスコメント先頭に `# <URL>` を1行入れる。
  - クラスがない場合：body の一番上に区切り線で囲んで書く。

    ```
    # ------------------------------------------------
    # <URL>
    # ------------------------------------------------
    ```
  - ただし`00-input`の入力系スニペットは、区切り線なしで`# <URL>`の1行のみとする。
  - 追加・変更したスニペットは、コンテスト開始前に`main`へpushしておく。
- **展開後すぐ実行できる状態**にする（未定義変数・要編集箇所を残す場合は`$1`等のプレースホルダで明示する）。
- コメントは日本語で簡潔に。計算量・注意点（オーバーフロー、0-indexed/1-indexed、破壊的操作かどうか）など、コードだけでは分からない情報のみ書く。

## 品質保証

- 追加・変更したら`.vscode/_check_syntax.py`を実行し、Python構文として妥当かを確認する。
- 可能であれば、検証済みの提出（AtCoderの提出URLやverify-library等）をdescriptionまたは本体コメントにリンクする。
- 既存スニペットと機能が重複する場合は、新規追加ではなく既存スニペットの改善・置き換えを検討する（重複が増えると`prefix`選択のコストが上がり、目的である「速さ」を損なう）。

## 新規追加の手順

1. `.vscode/99-template.code-snippets`の`Sample`をコピーし、該当カテゴリの`.code-snippets`ファイルに貼り付ける。
2. `prefix`・`description`・`body`を上記方針に沿って記述する。
3. `_check_syntax.py`で構文チェックする。
4. 可能なら実際にAtCoderの過去問等で動作確認する。
